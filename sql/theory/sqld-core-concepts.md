# 1. 데이터 모델링의 이해

## 1-1. 데이터 모델링이란?

- 정보시스템을 구축하기 위한 데이터 관점의 업무 분석 기법
- 현실 세계의 데이터를 약속된 표기법으로 표현하는 과정
- 데이터베이스를 구축하기 위한 분석 및 설계 과정

## 1-2. 데이터 모델링의 유의점

| 유의점 | 의미 | 설명 |
|---|---|---|
| 중복성 | 데이터 중복 | 동일한 데이터가 여러 곳에 저장되는 문제 |
| 비유연성 | 구조 변경의 어려움 | 업무 변화에 따라 데이터 구조를 쉽게 변경하지 못하는 문제 |
| 비일관성 | 데이터 불일치 | 동일한 데이터가 서로 다른 값으로 저장되는 문제 |

**암기:** 중복성 / 비유연성 / 비일관성

## 1-3. 데이터베이스 스키마 구조

| 구분 | 설명 |
|---|---|
| 외부 스키마 | 사용자나 응용 프로그램이 바라보는 개별적인 데이터 관점 |
| 개념 스키마 | 전체 데이터베이스의 논리적인 구조 |
| 내부 스키마 | 데이터가 실제로 저장되는 물리적인 구조 |

### 데이터 독립성

| 구분 | 관계 | 의미 |
|---|---|---|
| 논리적 데이터 독립성 | 외부 스키마 ↔ 개념 스키마 | 개념 스키마가 변경되어도 외부 스키마에 영향을 최소화 |
| 물리적 데이터 독립성 | 개념 스키마 ↔ 내부 스키마 | 내부 스키마가 변경되어도 개념 스키마에 영향을 최소화 |

**암기:** 외부-개념 = 논리적 / 개념-내부 = 물리적

## 1-4. ERD 작성 순서

1. 엔터티를 그린다.
2. 엔터티를 적절하게 배치한다.
3. 엔터티 간 관계를 설정한다.
4. 관계명을 기술한다.
5. 관계의 참여도를 기술한다.
6. 관계의 필수 여부를 기술한다.

## 1-5. 엔터티의 특징

1. 해당 업무에서 관리하고자 하는 정보여야 한다.
2. 유일한 식별자에 의해 식별할 수 있어야 한다.
3. 영속적으로 존재하는 인스턴스의 집합이어야 한다.
4. 업무 프로세스에 의해 이용되어야 한다.
5. 반드시 속성이 있어야 한다.
6. 다른 엔터티와 최소 한 개 이상의 관계가 있어야 한다.

### 엔터티 명명 규칙

- 업무에서 사용하는 용어를 사용한다.
- 약어 사용을 가급적 지양한다.
- 단수 명사를 사용하는 것이 일반적이다.
- 엔터티 이름만으로 의미를 명확하게 파악할 수 있어야 한다.

### 발생 시점에 따른 엔터티 분류

| 구분 | 설명 | 예시 |
|---|---|---|
| 기본 엔터티 | 업무에 원래 존재하는 독립적인 엔터티 | 고객, 상품 |
| 중심 엔터티 | 기본 엔터티로부터 발생하고 업무의 중심 역할을 하는 엔터티 | 주문, 계약 |
| 행위 엔터티 | 두 개 이상의 엔터티로부터 발생하는 업무 활동 정보 | 주문내역, 결제내역 |

## 1-6. 엔터티와 속성의 관계

- 하나의 엔터티는 두 개 이상의 인스턴스 집합으로 구성된다.
- 하나의 엔터티는 여러 개의 속성을 가질 수 있다.
- 하나의 속성은 하나의 속성값을 가진다.

### 속성의 특성에 따른 분류

| 구분 | 설명 | 예시 |
|---|---|---|
| 기본 속성 | 업무에서 원래 가지고 있는 속성 | 고객명, 생년월일 |
| 설계 속성 | 데이터 모델링 과정에서 새롭게 정의한 속성 | 상품코드, 일련번호 |
| 파생 속성 | 다른 속성의 값을 계산하여 생성한 속성 | 합계금액, 평균점수 |

**암기:** 기본 = 원래 존재 / 설계 = 새로 부여 / 파생 = 계산하여 생성

## 1-7. 데이터 모델링의 관계

### 관계의 구분

| 구분 | 설명 |
|---|---|
| 존재에 의한 관계 | 엔터티가 존재하기 때문에 형성되는 관계 |
| 행위에 의한 관계 | 업무 행위에 의해 형성되는 관계 |

ERD에서는 존재 관계와 행위 관계를 구분하지 않고 동일한 관계 표기법을 사용한다.

### UML 클래스 다이어그램의 관계

| 구분 | 표기 | 설명 |
|---|---|---|
| 연관관계 | 실선 | 지속적으로 관계를 유지하는 관계 |
| 의존관계 | 점선 | 상대방의 행위나 기능에 의존하는 관계 |

- 연관관계: 소스 코드에서 멤버 변수로 선언하여 사용할 수 있다.
- 의존관계: 메서드의 매개변수 등으로 상대 클래스를 이용할 수 있다.

### 관계 표기법

1. 관계명
2. 관계차수(관계의 수)
3. 선택성(필수 또는 선택 여부)

### 관계 도출 방법

| 구분 | 확인할 내용 |
|---|---|
| 명사 | 엔터티를 찾는다. |
| 동사 | 관계를 찾는다. |
| 연관 규칙 | 두 엔터티 사이에 업무적 연관성이 있는가? |
| 정보 조합 | 두 엔터티의 정보가 함께 사용되는가? |
| 관계 규명 | 실제 업무에서 관계를 명확하게 설명할 수 있는가? |

### 식별자 관계와 비식별자 관계

| 구분 | 식별자 관계 | 비식별자 관계 |
|---|---|---|
| 연결 방식 | 부모의 PK를 자식의 PK로 사용 | 부모의 PK를 자식의 일반 속성(FK)으로 사용 |
| 특징 | 부모의 식별자가 자식 식별자에 포함 | 부모의 식별자와 자식 식별자가 분리 |
| 예시 | 주문번호가 주문상세의 PK에 포함 | 고객번호가 주문의 FK로만 존재 |

**주의:** SQL JOIN을 최소화한다는 이유만으로 무조건 식별자 관계를 선택하는 것은 아니다. 업무 규칙과 데이터 모델의 특성을 고려해야 한다.

# 2. SQL 기본 개념

## 2-1. SQL의 순수관계 연산자

| 순수관계 연산자 | 의미 |
|---|---|
| SELECT | 조건에 맞는 행 선택 |
| PROJECT | 필요한 열 선택 |
| JOIN | 두 릴레이션을 연결 |
| DIVIDE | 특정 조건을 모두 만족하는 대상을 구하는 연산 |

## 2-2. 서브쿼리의 종류

| 구분 | 위치 | 설명 |
|---|---|---|
| 스칼라 서브쿼리 | SELECT 절 | 하나의 행, 하나의 컬럼 반환 |
| 인라인 뷰 | FROM 절 | 서브쿼리의 결과를 테이블처럼 사용 |
| 중첩 서브쿼리 | WHERE 절 등 | 조건을 만족하는 데이터를 조회 |

### 복수 행 연산자

| 연산자 | 의미 |
|---|---|
| IN | 여러 값 중 하나와 일치 |
| ANY | 조건을 만족하는 값이 하나라도 있으면 참 |
| ALL | 모든 값에 대해 조건을 만족해야 참 |

예시:

```sql
WHERE SAL > ANY (1000, 2000, 3000)
```

1000, 2000, 3000 중 하나보다 크면 참이다.

```sql
WHERE SAL > ALL (1000, 2000, 3000)
```

모든 값보다 커야 참이다.

## 2-3. 서브쿼리 사용 위치

서브쿼리는 다음 위치에서 사용할 수 있다.

- SELECT
- FROM
- WHERE
- HAVING
- ORDER BY

## 2-4. WHERE와 HAVING의 차이

| 구분 | WHERE | HAVING |
|---|---|---|
| 역할 | 행을 필터링 | 그룹을 필터링 |
| 집계함수 사용 | 직접 사용 불가 | 사용 가능 |
| 실행 개념 | 그룹화 이전 | 그룹화 이후 |

예시:

```sql
SELECT DEPTNO, SUM(SAL)
FROM EMP
WHERE SAL > 1000
GROUP BY DEPTNO
HAVING SUM(SAL) > 5000;
```

**주의:** GROUP BY와 집계함수를 사용하지 않고 HAVING만 사용했다고 반드시 오류가 발생하는 것은 아니다.

## 2-5. GROUP BY와 NULL

- GROUP BY는 NULL 데이터도 하나의 그룹으로 집계한다.
- NULL끼리 같은 그룹으로 취급한다.
- 집계함수 SUM, AVG, COUNT(컬럼) 등은 일반적으로 NULL을 무시한다.
- COUNT(*)는 NULL 여부와 관계없이 행의 개수를 센다.

### SUM과 NULL

```sql
SELECT SUM(COL1)
FROM TEST;
```

| COL1 |
|---|
| NULL |
| NULL |

결과: NULL

**이유:** SUM은 NULL을 무시하지만 계산할 숫자가 하나도 없기 때문이다.

```sql
SUM(NULL) = NULL
```

반면 다음과 같은 경우:

| COL1 |
|---|
| NULL |
| 20 |

결과는 20이다.

## 2-6. NULL과 빈 문자열

DBMS에 따라 처리 방식이 다르다.

| DBMS | 빈 문자열 '' |
|---|---|
| Oracle | NULL로 처리 |
| MySQL | NULL과 별개의 빈 문자열로 처리 |

Oracle에서는 다음과 같이 조회한다.

```sql
WHERE SERVICE_NAME IS NULL
```

MySQL에서는 빈 문자열과 NULL을 구분한다.

```sql
WHERE SERVICE_NAME = ''
```

```sql
WHERE SERVICE_NAME IS NULL
```

**주의:** SQLD에서 Oracle 기준 문제인지 확인해야 한다.

## 2-7. ORDER BY 숫자

ORDER BY 뒤에 숫자가 나오면 SELECT 절의 컬럼 위치를 의미한다.

```sql
SELECT ENAME, SAL, DEPTNO
FROM EMP
ORDER BY 2;
```

SAL이 두 번째 컬럼이므로 SAL 기준 오름차순 정렬이다.

| 구문 | 의미 |
|---|---|
| ORDER BY 1 | SELECT 첫 번째 컬럼 기준 |
| ORDER BY 2 | SELECT 두 번째 컬럼 기준 |
| ORDER BY 3 | SELECT 세 번째 컬럼 기준 |

## 2-8. CASE와 ORDER BY

ORDER BY 안에 CASE 문이 있다고 데이터 값이 변경되는 것은 아니다.

정렬 기준을 조건에 따라 변경하는 것이다.

```sql
ORDER BY
    CASE
        WHEN DEPTNO = 10 THEN 1
        WHEN DEPTNO = 20 THEN 2
        ELSE 3
    END;
```

부서번호가 10인 행을 먼저 정렬하고, 20인 행을 다음에 정렬한다.

## 2-9. 날짜와 시간 계산

Oracle DATE 자료형은 날짜뿐 아니라 시간도 저장한다.

| 계산식 | 의미 |
|---|---|
| 1 | 1일 |
| 1/24 | 1시간 |
| 1/(24*60) | 1분 |
| 1/(24*60*60) | 1초 |

예시:

```sql
SYSDATE + 1
```

현재 시간에서 하루 뒤

```sql
SYSDATE + 1/24
```

현재 시간에서 1시간 뒤

```sql
SYSDATE + 1/1440
```

현재 시간에서 1분 뒤

**암기:** 하루 = 24시간 = 1,440분 = 86,400초

# 3. JOIN과 집합 연산

## 3-1. JOIN의 종류

| JOIN | 설명 |
|---|---|
| INNER JOIN | 양쪽 테이블에서 조건이 일치하는 행 |
| LEFT OUTER JOIN | 왼쪽 테이블의 모든 행 + 오른쪽 일치 데이터 |
| RIGHT OUTER JOIN | 오른쪽 테이블의 모든 행 + 왼쪽 일치 데이터 |
| FULL OUTER JOIN | 양쪽 테이블의 모든 행 |
| CROSS JOIN | 두 테이블의 모든 조합 |
| NON EQUI JOIN | 등호가 아닌 비교 조건으로 연결 |

## 3-2. CROSS JOIN과 카타시안 곱

적절한 JOIN 조건이 없으면 카타시안 곱이 발생할 수 있다.

```sql
SELECT *
FROM EMP, DEPT;
```

```sql
SELECT *
FROM EMP
CROSS JOIN DEPT;
```

두 구문은 CROSS JOIN 결과를 생성한다.

예를 들어 EMP가 10행이고 DEPT가 4행이라면:

10 × 4 = 40행

## 3-3. INNER JOIN

```sql
SELECT *
FROM EMP E
INNER JOIN DEPT D
ON E.DEPTNO = D.DEPTNO;
```

양쪽 테이블의 DEPTNO가 일치하는 데이터만 조회한다.

## 3-4. LEFT OUTER JOIN

문제: 사원이 없는 부서 정보도 출력해야 한다.

```sql
SELECT *
FROM DEPT D
LEFT OUTER JOIN EMP E
ON D.DEPTNO = E.DEPTNO;
```

- DEPT를 기준으로 모든 부서를 출력한다.
- 해당 부서에 사원이 없으면 EMP 컬럼은 NULL로 출력한다.

**암기:** 왼쪽 테이블이 기준이다.

## 3-5. USING 조건절

```sql
SELECT *
FROM EMP E
JOIN DEPT D
USING (DEPTNO);
```

USING으로 연결한 공통 컬럼은 테이블 별칭이나 테이블 접두사를 붙일 수 없다.

잘못된 예:

```sql
SELECT E.DEPTNO
FROM EMP E
JOIN DEPT D
USING (DEPTNO);
```

올바른 예:

```sql
SELECT DEPTNO
FROM EMP E
JOIN DEPT D
USING (DEPTNO);
```

NATURAL JOIN도 공통 컬럼에 테이블 접두사를 붙이지 않는다.

## 3-6. NON EQUI JOIN

등호(=)가 아닌 비교 연산자를 사용하여 JOIN하는 방식이다.

예시:

```sql
SELECT *
FROM EMP E
JOIN SALGRADE S
ON E.SAL BETWEEN S.LOSAL AND S.HISAL;
```

급여가 특정 범위에 해당하는 급여 등급을 연결한다.

대부분의 경우 NON EQUI JOIN을 수행할 수 있지만 설계상의 이유로 수행이 불가능한 경우도 있다.

## 3-7. 집합 연산자

| 연산자 | 의미 |
|---|---|
| UNION | 중복 제거 후 합집합 |
| UNION ALL | 중복을 포함한 합집합 |
| INTERSECT | 교집합 |
| MINUS | 차집합 |

**암기:**

- UNION = 중복 제거
- UNION ALL = 중복 허용
- INTERSECT = 공통 데이터
- MINUS = 앞에는 있고 뒤에는 없는 데이터

### 1:1 양쪽 필수 관계

두 엔터티가 동일한 식별자 집합을 공유하고 모든 식별자가 양쪽에 반드시 존재한다면 다음과 같은 결과를 기대할 수 있다.

- A MINUS B = 공집합
- B MINUS A = 공집합
- A UNION B = A의 전체 건수
- A UNION ALL B = A의 전체 건수 × 2

단, 두 테이블의 데이터가 동일한 식별자 집합이라는 전제가 필요하다.

# 4. 계층형 질의

## 4-1. 계층형 SQL

계층형 구조를 표현하는 SQL이다.

```sql
SELECT *
FROM TEST
START WITH C2 IS NULL
CONNECT BY PRIOR C1 = C2;
```

| 구문 | 의미 |
|---|---|
| START WITH | 계층 구조의 시작 조건 |
| CONNECT BY | 부모와 자식의 연결 조건 |
| PRIOR | 이전 단계의 부모 행을 의미 |
| LEVEL | 현재 계층의 깊이 |

### PRIOR 이해하기

```sql
CONNECT BY PRIOR C1 = C2
```

현재 행의 C2가 이전 단계(부모 행)의 C1과 일치하는 데이터를 찾는다.

즉, 부모에서 자식 방향으로 내려간다.

```sql
CONNECT BY PRIOR C2 = C1
```

반대로 자식에서 부모 방향으로 연결하는 형태다.

### LEVEL

- ROOT 노드의 LEVEL은 1이다.
- 자식으로 내려갈 때마다 LEVEL이 1씩 증가한다.

## 4-2. ORDER SIBLINGS BY

```sql
ORDER SIBLINGS BY C3 DESC;
```

같은 부모를 가진 형제 행끼리 C3 기준으로 내림차순 정렬한다.

**주의:** 일반 ORDER BY와 달리 계층 구조의 부모-자식 관계를 유지하면서 형제 행만 정렬한다.

# 5. 윈도우 함수

## 5-1. 순위 함수

| 함수 | 설명 | 특징 |
|---|---|---|
| RANK() | 순위 | 동점이면 다음 순위 건너뜀 |
| DENSE_RANK() | 순위 | 동점이어도 다음 순위 건너뛰지 않음 |
| ROW_NUMBER() | 행 번호 | 각 행에 고유 번호 부여 |

예시: 점수가 100, 100, 90인 경우

| 점수 | RANK | DENSE_RANK | ROW_NUMBER |
|---|---:|---:|---:|
| 100 | 1 | 1 | 1 |
| 100 | 1 | 1 | 2 |
| 90 | 3 | 2 | 3 |

## 5-2. 분포 함수

| 함수 | 설명 |
|---|---|
| PERCENT_RANK | 상대적인 순위 비율 |
| CUME_DIST | 누적 분포 비율 |
| NTILE(N) | 데이터를 N개 그룹으로 분할 |

### NTILE 예시

```sql
NTILE(4) OVER (ORDER BY SAL DESC)
```

급여를 기준으로 내림차순 정렬한 후 4개 그룹으로 나눈다.

## 5-3. LAG와 LEAD

| 함수 | 의미 |
|---|---|
| LAG | 이전 행의 값 |
| LEAD | 다음 행의 값 |

예시:

```sql
LAG(SAL) OVER (ORDER BY SAL DESC)
```

현재 행을 기준으로 이전 행의 SAL을 가져온다.

```sql
LEAD(SAL) OVER (ORDER BY SAL DESC)
```

현재 행을 기준으로 다음 행의 SAL을 가져온다.

### LAG의 두 번째 인자

```sql
LAG(A.SAL, 2) OVER (ORDER BY SAL DESC)
```

현재 행을 기준으로 2행 이전에 있는 A.SAL 값을 가져온다.

```sql
LAG(A.SAL, 1)
```

1행 이전

```sql
LAG(A.SAL, 2)
```

2행 이전

```sql
LAG(A.SAL, 3)
```

3행 이전

## 5-4. RATIO_TO_REPORT

```sql
RATIO_TO_REPORT(SAL) OVER ()
```

전체 급여 합계에서 해당 행의 급여가 차지하는 비율을 계산한다.

예를 들어 전체 급여 합계가 10,000이고 현재 행의 SAL이 2,000이라면:

2,000 / 10,000 = 0.2 (20%)

## 5-5. PARTITION BY

그룹별로 나누어 계산하는 기능이다.

```sql
ROW_NUMBER() OVER (
    PARTITION BY DEPTNO
    ORDER BY SAL DESC
)
```

- PARTITION BY DEPTNO: 부서별로 그룹을 나눈다.
- ORDER BY SAL DESC: 각 부서 안에서 급여 내림차순 정렬한다.
- ROW_NUMBER(): 각 부서 안에서 순번을 부여한다.

## 5-6. 윈도우 프레임

| 구문 | 의미 |
|---|---|
| UNBOUNDED PRECEDING | 처음 행부터 |
| CURRENT ROW | 현재 행 |
| UNBOUNDED FOLLOWING | 마지막 행까지 |
| N PRECEDING | 현재 행 기준 N행 이전 |
| N FOLLOWING | 현재 행 기준 N행 이후 |

### 누적 합계

```sql
SUM(SAL) OVER (
    ORDER BY SAL
    ROWS BETWEEN UNBOUNDED PRECEDING
    AND CURRENT ROW
)
```

처음 행부터 현재 행까지 누적 합계를 계산한다.

### 현재 행 하나만 계산

```sql
SUM(SAL) OVER (
    ROWS CURRENT ROW
)
```

현재 행 하나만 대상으로 계산한다.

### 앞뒤 범위 지정

```sql
SUM(SAL) OVER (
    ORDER BY SAL
    RANGE BETWEEN 10000 PRECEDING
    AND 10000 FOLLOWING
)
```

현재 행의 SAL을 기준으로 값의 범위가 10,000 작은 값부터 10,000 큰 값까지 포함하여 계산한다.

**중요한 차이**

- ROWS: 물리적인 행의 개수 기준
- RANGE: ORDER BY 값의 논리적인 범위 기준

# 6. SQL에서 자주 나오는 기타 개념

## 6-1. 복합 컬럼 IN 조건

```sql
(JOIN_YMD, JOIN_HH)
IN (('20141201', '00'))
```

두 개의 컬럼을 하나의 묶음으로 비교한다.

| JOIN_YMD | JOIN_HH | 결과 |
|---|---|---|
| 20141201 | 00 | TRUE |
| 20141201 | 01 | FALSE |
| 20141202 | 00 | FALSE |

일반적인 IN:

```sql
WHERE SVC_ID IN ('A', 'B')
```

복합 컬럼 IN:

```sql
WHERE (COL1, COL2) IN (
    ('A', '1'),
    ('B', '2')
)
```

COL1과 COL2의 조합이 일치해야 한다.

## 6-2. 뷰(View)

뷰는 실제 데이터를 직접 저장하는 테이블이 아니라 SELECT 문을 기반으로 생성한 가상 테이블이다.

### 뷰의 장점

| 장점 | 설명 |
|---|---|
| 독립성 | 데이터 구조 변경에 따른 영향을 줄일 수 있음 |
| 편리성 | 복잡한 SQL을 단순하게 사용할 수 있음 |
| 보안성 | 사용자에게 필요한 데이터만 제공할 수 있음 |

## 6-3. DROP / TRUNCATE / DELETE

| 구분 | DROP | TRUNCATE | DELETE |
|---|---|---|---|
| 대상 | 테이블 구조와 데이터 | 테이블 데이터 | 테이블 데이터 |
| WHERE | 불가능 | 불가능 | 가능 |
| 테이블 구조 | 삭제 | 유지 | 유지 |
| 데이터 전체 삭제 | O | O | 조건에 따라 |
| ROLLBACK | 일반적으로 불가능 | 일반적으로 불가능 | 가능 |
| 명령 종류 | DDL | DDL | DML |

### 쉽게 외우기

**DROP = 집을 부순다.**

- 테이블 자체를 삭제한다.
- 구조와 데이터 모두 사라진다.

**TRUNCATE = 집은 놔두고 싹 비운다.**

- 테이블 구조는 유지한다.
- 데이터 전체를 삭제한다.
- WHERE를 사용할 수 없다.

**DELETE = 필요한 것만 골라 버린다.**

- WHERE 조건으로 특정 데이터 삭제 가능
- ROLLBACK 가능

주의: ROLLBACK 여부는 DBMS와 트랜잭션 설정에 따라 달라질 수 있다. Oracle 기준 시험에서는 위 표처럼 기억하면 된다.
